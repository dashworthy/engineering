# feature-doc

Say this first, plainly: `Using the feature-doc skill to author a designed feature/architecture PDF for <target>.`

You turn a **target** — a bundle, module, directory, or named feature — into an A4 PDF that reads like
a real architecture handoff: a cover, a plain-language overview, real vector diagrams (a component
map, an ER model, a process pipeline), the wire contract, a component→responsibility grid, the edge
cases a maintainer must act on, and how to test it. You author it by filling a fixed template, then
render it through the **`engineering:using-pdf-creation`** skill — you do not build the PDF machinery
yourself.

`$SKILL` is this skill's base directory (`${CLAUDE_PLUGIN_ROOT}/skills/feature-doc`). `$PDF` is the
PDF builder skill's directory (`${CLAUDE_PLUGIN_ROOT}/skills/using-pdf-creation`). `$RUNDIR` is the
per-render working directory the run-context script prints in step 2.

## One-time setup

The renderer lives in the `using-pdf-creation` skill; install its deps once (Node ≥ 18; a
Chromium-family browser is needed only because this doc uses diagrams):

```bash
cd "$PDF" && npm install
```

## The workflow

### 1. Understand the target — read the real code

Before authoring a word, map the feature from the source, not from memory:

- The entry points (controllers, commands, endpoints), the core services, and what they depend on.
- The data model (entities, ownership, invariants) — enough for a real ER diagram.
- The process flow from trigger to result — enough for a real pipeline diagram.
- The wire contract (request/response, config payloads) and the classes that carry each responsibility.
- The edge cases and failure modes the code actually handles, and how the feature is tested.

**Describe what the code does — never invent behavior.** If the target already has a README, treat it
as a source, not gospel; verify against the code. If the human handed you material (a spec, notes),
use it, but still ground every claim in the target.

### 2. Scaffold a render run directory

```bash
sh "${CLAUDE_PLUGIN_ROOT}/scripts/run-context.sh" pdf <slug> --fresh
```

`<slug>` is a short kebab handle for the doc (e.g. `product-configurator`). `--fresh` returns a fresh
numbered leaf `.engineering/<run>/pdf/<NNN>/`; the command prints its absolute path — call it `$RUNDIR`.

### 3. Author `pdf.tsx` from the template

Copy the template in and fill it:

```bash
cp "$PDF/references/templates/feature-doc.pdf.tsx" "$RUNDIR/pdf.tsx"
```

The template is split into a **DATA** block (cover, ToC, diagram sources, code samples) and a
**WIRING** block (the JSX tree — leave it alone for a standard doc). Fill the DATA, then replace the
placeholder prose in each section:

- Replace **every** `<...>` angle placeholder and `TODO —` line with real content, or delete the line.
- **Drop any OPTIONAL section** the feature doesn't need (e.g. set `ER_SOURCE = null` to omit the data
  model). A shorter true doc beats a padded one.
- Diagrams are real: rewrite `CHART_ARCH`, `CHART_FLOW`, and `ER_SOURCE` to model the actual system.
- Keep the file **self-contained** — import only from `@engineering/using-pdf-creation`, no relative
  imports or local asset files. The full component catalog and a when-to-use matrix live in
  **`$PDF/references/authoring.md`**; the fixture `$PDF/src/docs/configurator.pdf.tsx` is a worked
  example of the same shape against real content.
- **Never add a footer or a "generated by" line.** Page numbers are automatic (the body pages are
  numbered from 1; the cover and ToC are not). Author/date metadata belongs on the cover's `meta` strip.

### 4. Ask the reader: light or dark

**Always ask, every render — the default is light.** Put it as a structured choice following
`engineering:using-questions` (recommended answer first, a free-form escape, and the plain-text
fallback when no question tool is available):

- **Light** *(default, recommended)* — for print and most handoffs.
- **Dark** — for on-screen reading.

Render only the chosen theme (step 5). Do not render both unless the reader asks.

### 5. Render the chosen theme

```bash
cd "$PDF" && node --import tsx src/pdf/render.ts "$RUNDIR" --theme <light|dark>
```

Run it from `$PDF` so `tsx` and the package resolve; `$RUNDIR` is absolute, so the cwd change is safe.
This writes `$RUNDIR/pdf-<theme>.pdf`. A bad mermaid diagram aborts the render naming it — fix and re-run.

### 6. Fill the table of contents — a second pass

react-pdf resolves a cross-reference page number only after layout, so the ToC's `page` values start
as `'—'`. After the first render, open the PDF, read the **body-relative** page each section lands on
(the printed number, where 1 is the first body page), enter those into the `TOC` array, and re-render.

### 7. Verify — always look at the PDF

Do not claim success from the exit code. Inspect the rendered theme: the cover and ToC are unnumbered,
body pages are numbered from 1, diagrams render as diagrams fully inside their cards, no content
overflows the page, and no placeholder (`<...>` or `TODO`) survived. The full inspection protocol is
in **`$PDF/references/verifying.md`**. Fix and re-render until it holds.

## Where the rest lives

- **`$PDF/references/templates/feature-doc.pdf.tsx`** — the template you copy and fill (it lives with
  the PDF builder skill as a reusable template).
- **`$PDF/references/authoring.md`** — the component catalog + when-to-use matrix.
- **`$PDF/references/verifying.md`** — the inspection protocol.
