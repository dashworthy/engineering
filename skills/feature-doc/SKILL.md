# feature-doc

Say this first, plainly: `Using the feature-doc skill to author a feature/architecture document for <target>.`

You turn a **target** — a bundle, module, directory, or named feature — into an architecture handoff:
a cover, a plain-language overview, real diagrams (a component map, an ER model, a process pipeline),
the wire contract, a component→responsibility grid, the edge cases a maintainer must act on, and how
to test it. You own the **template**; `engineering:using-doc-creation` owns the **rendering**. You fill
the template, then hand it to that skill to produce the document — you do not build the render
machinery yourself.

- `$SKILL` is this skill's base directory (`${CLAUDE_PLUGIN_ROOT}/skills/feature-doc`); its templates
  live under `$SKILL/references/templates/`.
- `engineering:using-doc-creation` is the doc toolkit that renders the filled template.

## 1. Understand the target — read the real code

Before authoring a word, map the feature from the source, not from memory:

- The entry points (controllers, commands, endpoints), the core services, and what they depend on.
- The data model (entities, ownership, invariants) — enough for a real ER diagram.
- The process flow from trigger to result — enough for a real pipeline diagram.
- The wire contract (request/response, config payloads) and the classes that carry each responsibility.
- The edge cases and failure modes the code actually handles, and how the feature is tested.

**Describe what the code does — never invent behavior.** If the target already has a README, treat it
as a source, not gospel; verify against the code. If the human handed you material (a spec, notes),
use it, but still ground every claim in the target.

## 2. Fill this skill's template

Start from the template that matches the format you'll render:

- **`$SKILL/references/templates/pdf/feature-doc.pdf.tsx`** — the PDF template (JSX authored against
  the `engineering:using-doc-creation` component library).
- **`$SKILL/references/templates/markdown/feature-doc.md`** — the plain-GFM Markdown template.

The two carry the same section list — pick by the format the reader needs; both templates carry their
own fill-in instructions in a header comment. Fill in real content:

- Replace **every** `<...>` angle placeholder and `TODO —` line with real content, or delete the line.
- **Drop any OPTIONAL section** the feature doesn't need (e.g. omit the data model when there's no
  meaningful one). A shorter true doc beats a padded one.
- Diagrams are real: model the actual system (a bad mermaid diagram aborts a PDF render naming it).
- **Never add a footer or a "generated by" line.** Author/date metadata belongs on the cover.

## 3. Render via using-doc-creation

Hand the filled template to **`engineering:using-doc-creation`** and follow its workflow for the chosen
format — it owns format selection (PDF by default, Markdown otherwise), the render, and the
verification protocol (for a PDF, always look at the output before claiming success). This skill does
not reimplement any of that.
